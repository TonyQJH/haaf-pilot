## Abstract

### 这一段写什么

摘要最好就 **1 段，5–6 句**。

* **第 1 句**：说背景。Agent 正在进入真实工作流、工具调用、开放环境，所以 trustworthiness 变成 deployment-level 问题。
* **第 2 句**：说现有问题。现有评测是碎片化的，只测 code、hallucination、jailbreak、tool use 等单轴能力。
* **第 3 句**：点出你真正的核心论点。问题不只是“维度不够多”，而是**evaluation distribution 不具代表性**。
* **第 4 句**：提出你的 big idea：一个 **Holographic Agent Assessment Framework**，在一个 **representative socio-technical scenario manifold** 上评估 agent。
* **第 5 句**：概括你的框架核心组成：multi-layer assessment + distribution-aware scenario generation + diagnostic outputs。
* **第 6 句**：说意义。这个框架能把 agent evaluation 从“单点打分”推进到“部署可信度画像”，为 KDD 社区建立新的研究方向。

### 这一段的作用

摘要必须直接回答评审脑子里的 4 个问题：

* 你发现了什么根本问题？
* 你的新 idea 是什么？
* 为什么这不是普通 benchmark paper？
* 成功以后会改变什么？

## 1. Introduction: **The Missing Principle in Agent Evaluation**

这一节建议 3–4 段。

### 第 1 段写什么

开门见山，讲 **为什么现在必须讨论 agent trustworthiness**。

你可以写：

* agent 不再只是回答问题，而是在做多步规划、调用工具、访问外部环境；
* 一旦进入真实任务，失败就不再只是“答错题”，而可能是错误执行、目标漂移、资源误用、越权操作、社会偏见；
* 所以 trustworthiness 必须被放到真实部署条件下重新定义。

这段是“背景 + stakes”。

---

### 第 2 段写什么

讲 **现有评测为什么不够**。

这里可以用你那个很好的比喻：
**current agent evaluation is a blind-men-and-the-elephant problem**。

具体展开：

* 有的 benchmark 测能力，
* 有的测安全，
* 有的测 prompt injection，
* 有的测幻觉，
* 但它们大多是**孤立维度、孤立任务、孤立环境**。

结论要落在一句强话上：
**high benchmark scores do not imply deployment trustworthiness.**

---

### 第 3 段写什么

这里要把问题从“benchmark 不全面”提升为一个更学术的命题：

> 真正缺失的不是更多 case，而是一个关于 **representativeness** 的科学原则。

这一段要讲：

* agent trustworthiness 不是一个单点属性；
* 它是 agent 在一类**社会—技术场景分布**上的表现；
* 如果 benchmark 的采样分布和真实部署分布不对齐，那再高分也可能给出虚假的安全感；
* 尤其是**低频高危场景（black-swan / tail risks）**，传统 benchmark 最容易漏掉。

这一段是全文的理论转折点，非常重要。

---

### 第 4 段写什么

最后一段用来写 **本文贡献和路线图**。

不要写成传统 contributions list 那种“we implement X/Y/Z”。
要写成：

* 本文提出一个新的 evaluation paradigm；
* 我们把 trustworthiness 定义为对 representative scenario manifold 的估计问题；
* 我们提出一个全息式、多层评估框架；
* 我们提出一种 distribution-aware 的场景生成/采样机制；
* 我们说明该框架如何支持 blind-spot discovery、failure attribution 和 closed-loop improvement。

这样收尾，顺便把全文结构带出来。

## 2. Related Work

这一节建议 2–3 段。

**Benchmark Fragmentation and the Representativeness Gap**
### 第 1 段写什么

给现有工作做一个**极简分类**，不要展开太多文献细节。

比如你可以把现有 agent evaluation 分成几类：

* capability-centric benchmarks
* adversarial / jailbreak evaluations
* hallucination / factuality evaluations
* tool-use / planning benchmarks
* social or alignment-oriented evaluations

重点不是综述，而是说：**这些评测都只看“局部切片”**。

---

### 第 2 段写什么

讲这些评测共同漏掉了什么：

* 缺少**跨步骤轨迹级失败**分析；
* 缺少**环境约束**（资源、延迟、噪声、权限）；
* 缺少**多人/社会互动**场景；
* 缺少对**真实场景分布**的建模；
* 缺少把“常见任务”和“低频高危任务”统一纳入同一评价框架的能力。

最后一句可以非常有力：
**The bottleneck of agent trustworthiness is no longer metric design alone, but distribution design.**

---

### 第 3 段写什么（可选）

如果版面够，这一段专门定义 **representativeness gap**。

你可以写成一个概念段：

* benchmark measures performance on a curated set;
* deployment requires robustness over a heterogeneous, heavy-tailed scenario space;
* the gap between these two distributions is the representativeness gap.

这一段非常 KDD，因为它把问题变成了一个“数据分布 + 采样 + 覆盖”的问题。

---

## 3. **Holographic Agent Assessment Framework**

这一节是全文核心，建议占最大篇幅。
如果篇幅允许，可以有 4–5 个小节；如果太紧，就用段内小标题。

---

### 3.1 **Overview: Trustworthiness over a Scenario Manifold**

### 这一段写什么

先不要急着进四层，先给一个统一视角。

你要先定义：
你的 framework 不是一个 benchmark 集合，而是一个 **mapping**：

* 输入：一个 agent + 一个 scenario manifold；
* 过程：在不同评估层面对 agent 进行 probing；
* 输出：一个多维 trustworthiness profile，而不是单一分数。

这里建议你明确 scenario manifold 的维度，比如：

* task type
* tool interface
* interaction depth
* adversarial pressure
* resource constraints
* social context
* consequence severity / risk level

这段相当于“世界观定义”。

---

### 3.2 **Layer 1: Static Cognitive and Policy Analysis**

### 这一段写什么

这一层不要写得太像“必须 white-box access”，因为很多 agent 没法真的看内部推理。
建议你写得稍微稳一点：

* inspect system instructions, safety policies, memory interfaces, retrieval sources, or observable decision rationales when available;
* 目的是在真正运行前发现潜在偏差、目标冲突、边界不清、规则自相矛盾的问题；
* 这层评估的是 agent 的“latent vulnerability surface”。

如果你想保留 “Cognitive Anatomy”，可以写成一个概念词，但别把它说死成必须看 CoT。
更稳的表述是：
**reasoning traces or policy-visible decision structure when available**。

---

### 3.3 **Layer 2: Interactive Sandbox Simulation**

### 这一段写什么

这是你最容易写扎实的一层。

这一段要讲：

* 这层不是只做 attack benchmark，而是做 **scenario reproduction**；
* 包含正常复杂任务（可靠性）；
* 包含对抗输入 / prompt injection（鲁棒性）；
* 包含资源限制、延迟、工具异常（效率与稳定性）；
* 通过一个 world model library，把 OS、web、database、API 等接口统一起来。

注意一个措辞：
不要只说“攻击成功率”，要强调
**trajectory-level failures under realistic interaction dynamics**。
这比普通安全 benchmark 更像 Blue Sky 的“开放世界评估”。

---

### 3.4 **Layer 3: Social and Ethical Alignment**

### 这一段写什么

这一段的作用是把你的 paper 从“系统 benchmark”抬升到“社会—技术 trustworthiness”。

你要强调：

* 真实 agent 很多时候不是单独工作的，而是在多人环境、人机协作、agent-agent 协作中运行；
* 因此 trustworthiness 不能只看个体任务成功率；
* 还要看 bias、manipulation resistance、collusion、delegation failure、value drift。

这一段最好点两个高风险应用场景，例如：

* hiring / recruitment
* finance / lending
* healthcare triage
* workflow delegation

这会让评审更容易感到“这个问题真的大”。

---

### 3.5 **Layer 4: Distribution-Aware Representative Sampling**

### 这一段写什么

这一段一定要写成**本 paper 的核心引擎**。
这是你最像 KDD、也最像 Blue Sky 的地方。

这一段要明确讲：

* 不能靠手工列 100 个 case 来评估 agent；
* 真正难的问题是：**如何从一个巨大、长尾、异质的场景空间里，采出既有代表性、又对风险敏感的测试集**；
* 采样目标不仅包括高频场景，也包括低频但高危的 black-swan cases；
* 采样依据可以来自日志、任务分布、风险估计、交互复杂度、社会后果等。

这一段里你最好有一个核心 claim：

> representative evaluation should optimize both coverage and risk sensitivity.

也就是说，不是“覆盖越多越好”，而是要同时考虑：

* 头部常见任务是否覆盖，
* 长尾危险任务是否覆盖，
* 不同类型失败是否可区分，
* 采样结果是否可复现、可扩展。

**这段一定要比其他 layer 更长。**
否则你的 paper 会看起来像“4 个模块平铺”，而不是一个真正的 Blue Sky 命题。

---

## 4. **Experiments**
这一节建议 2–3 段。
主要讲: **Diagnostic Outputs and Illustrative Evaluation Agenda**

---
Layer 4 defines what we should test (representative scenarios); Layers 1–3 define how we test (signals and probes); Experiments 1–3 show why it matters (coverage, attribution, and closed-loop improvement).
### 第 1 段写什么

写 **Coverage & Blind-Spot Analysis**。

你可以说：

* 用现有 benchmark 和你的 framework 分别评估几个 representative agents；
* 目标不是刷榜，而是展示“高分 agent 仍然有系统性盲点”；
* 输出形式是 trustworthiness radar / multi-dimensional profile。

这一段强调的是：
**你这个框架能发现传统 benchmark 看不见的缺口。**

---

### 第 2 段写什么

写 **Vulnerability Attribution**。

这里讲：

* 对输入做语义保持扰动；
* 记录失败轨迹中的 tool calls 和 decision transitions；
* 把失败分类到 instruction drift、hallucination、malicious steering、boundary failure 等类型；
* 输出一个 failure taxonomy heatmap。

这段很重要，因为它说明你的框架不只是“判分”，而是能做**根因诊断**。

---

### 第 3 段写什么

写 **Closed-Loop Improvement**。

这里讲：

* 一个好的 trustworthiness framework 不应该只告诉我们“坏在哪”，还应该支持“如何修”；
* 你可以把评估结果用于 prompt hardening、sandbox policy design、tool routing guardrails、adversarial training 等；
* 再次评估后看 trustworthiness 是否提升，同时 utility 是否保持。

这一段的作用是告诉评审：
你的想法不是一个静态 benchmark，而是一个**能驱动 agent engineering 的研究闭环**。

---

## 5. **Discussion**
**Why This Is a Blue Sky Idea for KDD**

这一节非常重要。
因为这个 track 明确问了：

* why blue sky?
* why now?
* why KDD?
* success looks like what?

所以这一节最好别省。

建议 2–3 段。

---

### 第 1 段写什么

直接回答 **Why Blue Sky?**

可以写：

* 这不是一篇普通 benchmark paper；
* 也不是一个 incremental dataset paper；
* 它真正提出的是一个新的 scientific unit of analysis：
  **agent trustworthiness should be measured over representative deployment distributions rather than isolated benchmark instances.**

这句话非常关键，建议你在文中明确写出来。

---

### 第 2 段写什么

回答 **Why now?**

讲：

* agent 已经从静态 QA 进入开放式工具使用；
* 当前评测体系延续了 LLM-era 的“题库式打分逻辑”，但这对 agent 已经不够；
* 如果不解决 representativeness 问题，社区会继续得到“高分但不可信”的系统。

这段会让评审觉得你不是空想，而是在回应一个马上会爆炸的问题。

---

### 第 3 段写什么

回答 **Why KDD?** 和 **What does success look like?**

先对应 KDD 主题：

* **Foundations of Knowledge Discovery and Data Science**：你重新定义了 evaluation 的对象与覆盖问题；
* **Trustworthy and Responsible Data Science**：你直接服务于可信 agent 评测；
* **Systems for Data Science and Scalable AI**：你需要 sandbox/world model/evaluation pipeline；
* **Data Science Applications**：你的场景覆盖真实工作流应用。

然后写成功图景：

* 社区形成统一的 scenario taxonomy；
* 有共享的 world model library；
* 有 risk-aware coverage metrics；
* benchmark 不再只报单一 score，而是报 trustworthiness profile；
* 后续几年出现一批围绕该框架的 dataset、sampling algorithms、diagnostic tools 和 defense methods。

这一段是 Blue Sky 味道最浓的一段。

---

## 6. **Conclusion**

### 这一段写什么

结尾就 1 段，别长。

你要做三件事：

* 重申问题：当前 agent evaluation 仍然是碎片化、非代表性的；
* 重申主张：trustworthiness 必须在 representative socio-technical manifolds 上定义与估计；
* 重申影响：Holographic evaluation 提供了一个让 KDD 社区共同推进的新研究方向。

最后一句一定要收得有力量一点，例如那种：

* 没有 representative evaluation，就没有可信部署；
* 没有 deployment-aligned trustworthiness，就没有真正可落地的 agentic AI。

## 注意事项

1. **过细的实验执行细节**
   Blue Sky 不是 regular paper，不需要写得像完整 benchmark report。

2. **大段 Related Work**
   5 页太宝贵，相关工作并入第 1、2 节就够了。

## 需要改写得更稳的地方

1. **“White-box inspection / CoT anatomy”**
   不要写得像你默认所有 agent 都能看内部推理。
   改成更一般化的 “policy-visible reasoning traces or decision rationales when available”。

2. **四层关系**
   不要平铺。
   最好写成：
   **Layer 4 是核心采样引擎，Layer 1–3 是在这个代表性场景空间上的不同 probing interfaces。**

# 最后给你一句最重要的写作原则

整篇 paper 要不断重复同一个核心句式：

> **The central challenge is not merely evaluating more dimensions, but evaluating agents over representative socio-technical distributions.**

你只要把这句话贯穿 Abstract、Introduction、Framework、Why Blue Sky，整篇文章的气质就会从“综合 benchmark 方案”升级成“一个新的研究议程”。
